## What it proves

End-to-end, on a real bot match:

    game-server StatsReporter → P1 ingest API → Postgres → P3 admin read layer → /admin dashboards

- kill events + per-weapon counters land in Postgres;
- `/admin/api/weapons` (weapon balance) reports non-zero kills with a sane hit-rate;
- `/admin/api/combat` reports kill-distance stats (count>0, populated histogram) + hitzone totals;
- **faithfulness:** Σ `weapon_balance.total_kills` == SQL Σ `match_player_weapons.kills`, and
  `/admin/api/combat` `kill_distance.count` == SQL count of kill events;
- the admin HTML pages render 200 with a seeded weapon;
- the **auth gate holds**: with `ADMIN_DEV_OPEN` off and no session cookie, `/admin/api/weapons` and
  `/admin` both return **403**.

## How to run

```bash
cd /path/to/blockfire
./docker/run-stats-p3-gate.sh          # brings up bf-p3 stack (ADMIN_DEV_OPEN=1) + plays a 24-bot match
```

Backend stack runs under docker-compose project `bf-p3` (db/api/worker); the game server + a separate
bot-driver run on the host over a distinct game port (`28323`, clear of the P1 `28123` / P2 `28223` gates so
a concurrent agent is never disturbed). The native snapshot-encoder `.so` must be present in the checkout
(`native/snapshot_encoder/target/release/libsnapshot_encoder.so` — `target/` is gitignored, so copy it in).

## Notes

- Headless bot matches are combat-light by design (we prove mechanics deterministically and don't gate on
  emergent bot AI — see the project's testing philosophy). Six kills across 24 bots is enough to prove the
  admin surface is faithful to the raw tables; the weapon-balance / combat / hitzone numbers above are all
  cross-checked against direct SQL.
- Weapon keys are the in-repo **variant** names (`m4a2`, `m245 saw`, …) flowing through from the P1-B producer.
- `ADMIN_DEV_OPEN=1` is the dev/LAN escape hatch used here; production admin is the SteamID allowlist
  (`ADMIN_STEAM_IDS`). The 403 step recreates the api with the escape hatch off to prove the gate closes.
